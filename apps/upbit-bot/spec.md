## 1. 개요
업비트 **공개 시세 API·웹소켓**의 실시간 가격으로 **가상 잔고 모의투자 자동매매**를 돌리는 웹앱이다. 변동성 돌파·이동평균 교차·RSI 세 가지 전략 중 하나를 골라 봇을 켜면, 전략이 신호를 낼 때 가상으로 사고팔고 매매 로그와 수익률을 보여준다. 같은 폴더의 **로컬 Node.js 서버(`server/`)** 를 자기 PC에서 실행하면 같은 화면에서 **실거래 모드**로 전환할 수 있으며, API 키는 PC의 `.env`에만 둔다. 순수 HTML/CSS/JS로 `apps/upbit-bot/` 안에서 자체 완결되고 블로그 메인에 iframe 카드로 들어간다(블로그에서는 모의투자만 동작).

### 1.1 왜 실거래는 로컬 서버인가
- 업비트 **개인(Exchange) API는 브라우저 CORS를 지원하지 않는다** → 브라우저에서 직접 주문 불가.
- API 키마다 **허용 IP 등록**이 필요하다 → 사용자의 PC(고정 공인 IP)에서 호출해야 한다.
- 공개 페이지(GitHub Pages)에 키를 두면 즉시 유출된다 → 키는 PC의 `server/.env`에만, 브라우저·localStorage·저장소에는 절대 두지 않는다.

## 2. 기능 목록

### 2.1 시세·마켓
| 기능 | 구분 | 내용 |
|---|---|---|
| 마켓 선택 | 필수 | `GET /v1/market/all?isDetails=true` → `market`이 `KRW-`로 시작하는 것만. 한글명·영문명·코드 검색 가능한 `<select>` + 검색 입력(예: "비트", "BTC"). 기본 `KRW-BTC`. `market_warning`(유의 종목)이면 "유의" 배지 + 봇 시작 시 경고. 목록은 세션당 1회 조회 후 메모리 캐시(+ localStorage 24시간 캐시) |
| 실시간 현재가·등락률 | 필수 | 웹소켓 `ticker` 구독(2.1.1). 현재가, 전일 대비 등락률(`signed_change_rate`), 등락액, 24시간 거래대금(`acc_trade_price_24h`). 상승=빨강, 하락=파랑(국내 관례), 보합=회색. 가격 갱신 시 짧은 깜빡임(모션 줄이기 설정 시 생략) |
| 웹소켓 실패 시 대체 | 필수 | 연결 실패/끊김 시 지수 백오프(1→2→4→…최대 30초) 재연결. 재연결 중에는 `GET /v1/ticker?markets=` 를 **2초 간격** 폴링으로 대체, 상태 칩에 "실시간 끊김 · 폴링 중" |
| 캔들 차트 | 필수 | 아래 2.1.2 |

#### 2.1.1 웹소켓 사용 규칙
- 주소 `wss://api.upbit.com/websocket/v1`. `ws.binaryType = 'arraybuffer'`, 수신 데이터는 `new TextDecoder().decode()` 후 `JSON.parse` (업비트는 바이너리 프레임으로 보냄 **[확인 필요: 현재도 바이너리인지, 텍스트면 그대로 파싱 — 두 경우 모두 처리]**).
- 구독 메시지: `[{"ticket":"<uuid>"},{"type":"ticker","codes":["KRW-BTC"]},{"format":"SIMPLE"}]`. SIMPLE 포맷이면 필드명이 축약(`tp`=trade_price, `scr`=signed_change_rate 등)되므로 **기본 포맷(DEFAULT) 사용**을 권장(파싱 단순화). 마켓 변경 시 같은 연결로 새 구독 메시지 전송.
- 무응답 끊김 방지: 60초마다 텍스트 `"PING"` 전송 **[확인 필요: 업비트 idle timeout 120초·PING 지원]**.
- 체결 가격 기준: 전략·모의체결 모두 `trade_price`(최근 체결가) 사용.

#### 2.1.2 캔들 차트 — **추천: canvas 직접 그리기** [결정 D6]
- 이유: ① 외부 의존성 0(CLAUDE.md "최소화") ② 필요한 것은 캔들 + 이동평균선 2개 + 매수/매도 마커 + 변동성 돌파 목표가 수평선 + (RSI 선택 시) 하단 RSI 패널뿐이라 200~300줄로 충분 ③ 다크모드 색상을 CSS 변수에서 그대로 읽어 일관 유지.
- 대안: TradingView `lightweight-charts`(CDN, 버전 고정 `lightweight-charts@4.2.0` 등 **[확인 필요: 사용할 정확한 버전]**) — 줌/팬이 필요해지면 교체. 차트 모듈을 `ui/chart.js` 하나로 감싸 교체 가능하게 한다.
- 표시 범위: 전략의 캔들 단위로 최근 **120개**(데이터는 200개 조회). 가로 375px에서 캔들 폭 ≥2px.
- 구성: 상단 가격 패널(캔들, MA선, 목표가 점선, ▲매수/▼매도 마커), RSI 전략일 때만 하단 RSI 패널(30/70 가이드선). 우측 가격 축 4~5눈금, 하단 시간 축 3~4눈금(KST).
- 갱신: 현재 형성 중인 마지막 캔들은 실시간 가격으로 high/low/close 갱신, 캔들 마감 시 재조회(2.4).
- 터치/마우스 오버 시 해당 캔들의 시각·OHLC 툴팁 **[선택]**.
- `devicePixelRatio` 반영, `ResizeObserver`로 리사이즈 시 다시 그리기.
- 접근성: canvas에 `role="img"` + `aria-label="KRW-BTC 60분봉 차트, 현재가 …"` 갱신.

### 2.2 전략 (모두 **롱 온리**, 한 번에 최대 1포지션, 매수 1회 → 매도 1회 반복)
공통 규칙
- **캔들 정렬**: 업비트 캔들 API는 최신순으로 오므로 받은 즉시 **과거→최신 순으로 뒤집는다**.
- **마감 캔들만 사용**(변동성 돌파 제외): 응답의 가장 최신 캔들은 아직 형성 중이므로 지표 계산에서 제외한다. 판정: 최신 캔들의 `candle_date_time_utc` + 캔들 길이 > 현재 UTC 시각이면 미마감.
- 신호는 **교차(crossing) 순간 1회**만 발생(레벨 상태가 아니라 이전 값→현재 값 변화로 판단). 같은 캔들에서 신호 중복 처리 금지(마지막 처리한 캔들 시각 저장).
- 신호가 나도 이미 같은 방향 포지션이면 무시(보유 중 매수 신호 무시, 미보유 중 매도 신호 무시).
- 일봉 경계: 업비트 일봉은 **KST 09:00(UTC 00:00) 시작**.

#### 2.2.1 변동성 돌파 (Volatility Breakout)
| 항목 | 값 |
|---|---|
| 캔들 단위 | 일봉(`/v1/candles/days`) — 전일 고가·저가, 당일 시가 |
| 파라미터 | `K` 기본 **0.5** (범위 0.1~1.0, 0.05 단위) |
| 목표가 | `target = 당일 시가 + (전일 고가 − 전일 저가) × K` (호가 단위로 올림 처리하지 않고 계산값 그대로 비교, 표시만 호가 단위 반올림) |
| 진입 | 당일(KST 09:00~다음날 09:00) **미보유** 상태에서 실시간 `trade_price ≥ target` 이 처음 되는 순간 시장가 매수. **하루 1회만 진입**(당일 이미 진입했으면 청산 후 재진입 안 함) |
| 청산 | 다음 일봉 시작(KST 09:00:00) 이후 첫 평가 시 시장가 전량 매도 [결정 D12: 기본 09:00 직후 / 대안 08:59:30] |
| 필터 [선택] | 이동평균 필터: 당일 시가 > 일봉 종가 5일 이동평균일 때만 진입(기본 OFF) |
| 평가 주기 | 웹소켓 가격 수신마다(최대 초당 1회로 스로틀). 09:00:05 KST에 일봉 재조회로 새 목표가 계산 |
| 차트 | 일봉 차트 + 목표가 수평 점선 |

#### 2.2.2 이동평균 골든/데드크로스
| 항목 | 값 |
|---|---|
| 캔들 단위 | 기본 **60분봉**(`/v1/candles/minutes/60`). 선택지 15분/60분/240분/일봉 |
| 파라미터 | 단기 `short` 기본 **5**, 장기 `long` 기본 **20** (조건 `short < long`, 각 2~100). 단순이동평균(SMA), 종가 기준 |
| 진입(골든크로스) | 마감 캔들 기준 `직전 SMA_s ≤ 직전 SMA_l` 이고 `현재 SMA_s > 현재 SMA_l` → 다음 평가 시점에 시장가 매수 |
| 청산(데드크로스) | `직전 SMA_s ≥ 직전 SMA_l` 이고 `현재 SMA_s < 현재 SMA_l` → 시장가 전량 매도 |
| 평가 주기 | 캔들 마감 시각 + 3초에 캔들 재조회 후 1회 |
| 필요 캔들 수 | `long + 1` 개 이상의 마감 캔들(부족하면 "데이터 부족" 표시, 신호 없음) |
| 봇 시작 시점 처리 | 시작 시 이미 단기>장기 상태여도 **매수하지 않는다**(다음 교차까지 대기). 화면에 "현재 상태: 골든 구간(교차 대기)" 표시 |

#### 2.2.3 RSI 과매도/과매수
| 항목 | 값 |
|---|---|
| 캔들 단위 | 기본 **60분봉**. 선택지 15분/60분/240분/일봉 |
| 파라미터 | 기간 `period` 기본 **14**, 과매도 `low` 기본 **30**, 과매수 `high` 기본 **70** |
| 계산 | **Wilder 방식**: 첫 `period`개 변화량의 단순평균으로 avgGain/avgLoss 시작, 이후 `avg = (이전avg × (period−1) + 현재값) / period`. `RS = avgGain/avgLoss`, `RSI = 100 − 100/(1+RS)`. `avgLoss = 0`이면 RSI=100(둘 다 0이면 50). 정확도를 위해 마감 캔들 200개 전체로 계산 후 마지막 값 사용 |
| 진입 | `직전 RSI < low` 이고 `현재 RSI ≥ low` (과매도 탈출 상향 돌파) → 시장가 매수 |
| 청산 | `직전 RSI > high` 이고 `현재 RSI ≤ high` (과매수 이탈 하향 돌파) → 시장가 전량 매도 |
| 평가 주기 | 캔들 마감 + 3초 |
| 참고 | 하락장에서 장기간 청산 신호가 안 나올 수 있음 → 손절 [선택] 안내 문구를 전략 설명에 표시 |

#### 2.2.4 안전장치(전략과 별개, 엔진에서 적용)
| 항목 | 구분 | 기본값 | 내용 |
|---|---|---|---|
| 1회 최대 주문금액 | **필수** | 모의: 제한 없음 / 실거래: **50,000원** | 주문 금액이 넘으면 한도까지만 주문 [결정 D3] |
| 일일 최대 주문 횟수 | **필수** | 10회(매수+매도) | 넘으면 봇 자동 정지 + 로그 |
| 중복 주문 방지 | **필수** | — | 주문 진행 중(in-flight) 플래그가 켜져 있으면 새 주문 무시. 실거래는 `identifier`(봇ID+타임스탬프)로 재전송 중복 차단 |
| 손절(Stop-loss) | 선택 | OFF, 켜면 −3% | 평균 매수가 대비 현재가 ≤ −N%면 시장가 매도(실시간 평가) |
| 익절(Take-profit) | 선택 | OFF, 켜면 +5% | 사용자가 고르지 않은 기능이므로 기본 OFF |
| 일일 손실 한도 | 선택 | OFF, 켜면 −5% | 당일 실현 손익 ≤ −N%면 봇 정지 |
| 긴급 정지 | **필수** | — | "모두 정지" 버튼: 봇 정지 + (실거래) 미체결 주문 취소. 보유분은 자동 매도하지 않고 "보유분 시장가 매도" 버튼을 별도 제공(확인 대화상자) |

### 2.4 데이터 갱신 스케줄 · API 호출 제한 대응
- **실시간 가격은 웹소켓 1개 연결**로만 받는다(REST 폴링은 대체 수단).
- 캔들 재조회: 전략 캔들 마감 시각 + 3초에 1회, `count=200` 1요청. 차트가 다른 단위를 보더라도 동시 요청 최대 2개.
- 마켓 목록: 세션당 1회.
- 공통 요청 함수(`lib/upbit-public.js`)에 **요청 큐 + 토큰 버킷**(초당 최대 **5회**, 업비트 시세 API 한도의 절반 수준)으로 직렬화. 공개된 한도는 시세 조회 초당 10회(IP 단위)로 알려져 있으나 **[확인 필요]**. 코드에 한도를 고정하지 말고 응답 헤더 `Remaining-Req`(예: `group=candles; min=…; sec=…`)를 읽어 `sec ≤ 1`이면 다음 초까지 대기.
- `429 Too Many Requests` 수신 시 1초→2초→4초 백오프 후 최대 3회 재시도, 그래도 실패하면 로그 경고. `418`(일시 차단)이면 봇을 **자동 정지**하고 "업비트가 요청을 일시 차단했습니다" 안내.
- 실거래(서버 경유) 주문 API는 업비트 주문 그룹 한도(초당 8회로 알려짐 **[확인 필요]**)보다 훨씬 적게 사용(봇은 분당 수 회 이하).
- 탭이 백그라운드일 때 브라우저가 타이머를 늦출 수 있으므로, 캔들 마감 판정은 `setTimeout` 예약 시각이 아니라 **매 평가 때 현재 시각으로 다시 계산**한다.
- 공개 REST의 브라우저 CORS 허용: 업비트 시세 API는 `Access-Control-Allow-Origin`을 허용하는 것으로 알려져 있음 **[확인 필요 — Build 첫 작업으로 실제 브라우저에서 확인. 안 되면 사용자에게 알리고 중단]**.

### 2.5 업비트 거래 규칙 반영 (`lib/market-rules.js`)
| 규칙 | 값 | 비고 |
|---|---|---|
| 수수료 | KRW 마켓 **0.05%** (`FEE_RATE = 0.0005`) | 매수·매도 각각. 실거래는 시작 시 서버 `GET /api/chance`의 `bid_fee`/`ask_fee`로 덮어씀 **[확인 필요: 이벤트·등급별 변동]** |
| 최소 주문금액 | **5,000원** | 매수 주문액, 매도 시 `수량 × 현재가`가 5,000원 미만이면 매도 불가 → 로그 "잔량 소액(먼지)"로 처리하고 포지션 종료로 간주 |
| 수량 정밀도 | 소수 8자리 | 모의에서 수량은 `Math.floor(x × 1e8) / 1e8` |
| 호가 단위(KRW) | 아래 표 | 시장가 주문만 쓰므로 실거래 주문엔 직접 필요 없고, **목표가·가격 표시 반올림과 모의 체결가 정규화**에 사용 |

호가 단위 표 (기본값, **[확인 필요: 업비트가 2023~2024년에 일부 구간을 변경한 적이 있음. 가능하면 `GET /v1/orderbook/instruments`의 `tick_size`로 대체 — 엔드포인트 존재 여부도 확인 필요]**)

| 가격 구간(원) | 호가 단위 |
|---|---|
| 2,000,000 이상 | 1,000 |
| 1,000,000 ~ 2,000,000 미만 | 1,000 **(500일 수 있음, 확인 필요)** |
| 500,000 ~ 1,000,000 미만 | 500 **(100일 수 있음, 확인 필요)** |
| 100,000 ~ 500,000 미만 | 100 **(50일 수 있음, 확인 필요)** |
| 10,000 ~ 100,000 미만 | 10 |
| 1,000 ~ 10,000 미만 | 1 **(5일 수 있음, 확인 필요)** |
| 100 ~ 1,000 미만 | 0.1 **(1일 수 있음, 확인 필요)** |
| 10 ~ 100 미만 | 0.01 |
| 1 ~ 10 미만 | 0.001 |
| 0.1 ~ 1 미만 | 0.0001 |
| 0.1 미만 | 0.00001 (이하 자릿수 확인 필요) |

→ 표는 `market-rules.js` 상단 상수 하나에 모아 두고, 확인 후 값만 바꾸면 되게 한다.

모의 체결 규칙(`PaperBroker`)
- 체결가 = 주문 시점의 최신 `trade_price` × (매수 `1 + slippage` / 매도 `1 − slippage`), `slippage` 기본 **0**(설정 [선택] 0~0.5%).
- **시장가 매수**(금액 A 지정): 수수료 `fee = A × 0.0005`(원 단위 반올림 없이 계산, 표시만 원 단위), KRW 차감 = `A + fee`, 체결 수량 = `floor8(A / 체결가)`. (업비트 시장가 매수는 주문 총액과 별도로 수수료를 잠그는 방식으로 알려짐 **[확인 필요]** → 사용 가능 KRW의 `÷1.0005`로 주문액 결정)
- **시장가 매도**(수량 V): 총액 = `V × 체결가`, 수수료 = 총액 × 0.0005, KRW 증가 = 총액 − 수수료.
- 평균 매수가 = (기존 수량×기존 평단 + 신규 수량×체결가)/(합계 수량). 수수료는 평단에 넣지 않고 손익 계산 시 반영.
- 실현 손익(1회 왕복) = 매도 순수령액 − (매수 KRW 차감액 × 매도수량/매수수량).

### 2.6 모의/실거래 모드
- 헤더 우측 **모드 스위치** `[모의] [실거래]`. 기본 모의. 실거래 탭은 다음을 **모두** 만족해야 활성화:
  1. 페이지가 로컬 서버가 서빙한 주소(`http://127.0.0.1:{port}/` 또는 `http://localhost:{port}/`)에서 열렸다 [결정 D1 기본안]. GitHub Pages·iframe 안에서는 실거래 스위치를 비활성 + 툴팁 "실거래는 PC에서 로컬 서버를 실행한 뒤 사용할 수 있습니다(설명 보기)".
  2. `GET /health` 성공 + `keyConfigured: true`.
  3. 로컬 토큰 인증 성공(5.4).
- **서버 연결 상태 칩**: `● 서버 연결됨(DRY-RUN)` / `● 서버 연결됨(실주문)` / `○ 서버 없음` / `⚠ 인증 실패`. 10초마다 `/health` 확인, 3회 연속 실패 시 실거래 봇 자동 정지.
- **실거래 진입 절차**(모달 3단계):
  1. 경고문(10장 위험 고지 전문) 표시, 스크롤 끝까지 읽어야 다음 활성화.
  2. 체크박스 3개 모두 체크: "실제 자산으로 주문이 나갑니다" / "손실은 전적으로 제 책임입니다" / "API 키에 출금 권한이 없음을 확인했습니다".
  3. 입력란에 `실거래 시작`을 정확히 타이핑 → 확인.
  - 진입 후 화면 전체에 **빨간 상단 띠** "실거래 모드 · 실제 주문" 고정 표시, 배경색 미세 변경.
  - 실거래 봇 시작 시 한 번 더 확인 대화상자(금액·마켓 요약).
- 모드 전환은 봇 정지 상태에서만 가능. 모의/실거래 상태(잔고·로그)는 저장 키를 분리한다.
- 실거래 포지션 기준 [결정 D5 기본안]: **봇이 직접 산 수량만** 봇 포지션으로 추적하고, 매도도 그 수량(실제 잔고와 비교해 작은 값)만 한다. 사용자가 원래 보유하던 코인은 건드리지 않는다. 시작 시 서버 잔고를 조회해 표시만 한다.
- 실거래 주문 흐름: `POST /api/orders` → `uuid` 수신 → 1초 간격 최대 10회 `GET /api/order?uuid=` 로 `state`가 `done`(또는 시장가 매수의 `cancel`+체결수량>0 **[확인 필요]**)이 될 때까지 확인 → 체결 수량·평균가·수수료(`trades` 합산, `paid_fee`)로 포지션 갱신. 10회 안에 확정 안 되면 봇 일시정지 + 경고.

### 2.7 백테스트 — **필수(간이)** [결정 D8]
- 이유: 세 전략 중 무엇을 쓸지 고르는 근거가 필요하고, 전략 함수를 순수 함수로 만들면 추가 비용이 작다. 블로그 방문자에게도 볼거리.
- 입력: 현재 마켓·전략·파라미터, 해당 캔들 최근 **200개**(1요청). 초기 자금 1,000,000원, 수수료 0.05%, 슬리피지 설정값.
- 체결 가정: MA/RSI는 **신호 캔들의 다음 캔들 시가**에 체결. 변동성 돌파는 해당 일봉 `high ≥ target`이면 `target`가에 매수, **다음 일봉 시가**에 매도(마지막 날 보유분은 마지막 종가로 평가).
- 결과: 총 수익률, 거래 횟수, 승률, 최대 낙폭(MDD, 총자산 기준), 같은 기간 단순 보유(Buy & Hold) 수익률, 거래 목록 표, 차트에 매수/매도 마커.
- 문구: "과거 성과는 미래 수익을 보장하지 않습니다. 200개 캔들은 짧은 기간입니다." 상시 표시.
- [선택] 캔들 수를 400/600으로 늘리기(`to` 파라미터로 이어 받기, 요청 간 200ms 간격).

### 2.8 탭이 닫히면 봇이 멈춘다 — 정리
- 이 앱의 봇 루프는 **브라우저 탭 안의 JS**에서 돈다. 탭을 닫거나, 모바일에서 다른 앱으로 전환하거나, PC가 절전되면 봇이 멈춘다(백그라운드 탭은 타이머가 1분 단위로 느려질 수 있음).
- 1차 구현(기본안, [결정 D2]):
  - 봇 실행 중 `beforeunload` 경고("봇이 실행 중입니다. 닫으면 멈춥니다").
  - [선택] Screen Wake Lock API로 화면 꺼짐 방지(지원 브라우저만, 토글).
  - `visibilitychange`로 탭 복귀 시 즉시 재평가 + 캔들 재조회. 멈춰 있던 동안 놓친 신호는 **소급 체결하지 않고** 로그에 "중단 구간 hh:mm~hh:mm"만 남긴다.
  - 봇 상태(실행 여부·포지션·마지막 처리 캔들)를 localStorage에 저장 → 페이지를 다시 열면 "이전 실행 상태 복원(정지 상태로)" 배너, 사용자가 "재개"를 눌러야 다시 시작. 실거래는 재개 전 서버 잔고와 포지션을 대조.
  - 화면 상단 안내: "봇은 이 탭이 열려 있는 동안만 동작합니다."
- 대안(2차, 범위 밖 기본): 로컬 서버가 전략 루프를 직접 돌리는 **서버 상주 모드**. 전략 함수가 DOM 없는 ES 모듈이므로 Node에서 그대로 import 가능하게 설계해 두면 확장이 쉽다(3·4장 설계가 이를 전제로 함).

| 메서드·경로 | 업비트 호출 | 설명 |
|---|---|---|
| `GET /` , `GET /*.js|css|html` | — | `apps/upbit-bot/`(server의 상위 폴더) 정적 파일 서빙. `..` 경로 탈출 차단, `server/` 폴더 자체는 서빙 금지(`.env` 노출 방지) |

### 5.4 CORS · 요청 인증
- **기본안 [결정 D1]**: 앱을 서버가 직접 서빙하므로 **동일 출처** → CORS 불필요. `Access-Control-Allow-Origin` 헤더를 아예 보내지 않는다.
  - 이유: GitHub Pages(HTTPS 공개 사이트) → `http://localhost` 요청은 브라우저의 Private/Local Network Access 정책(Chrome 권한 프롬프트·차단), Safari의 혼합 콘텐츠 차단 등으로 브라우저마다 동작이 다르다 **[확인 필요]**. 동일 출처가 가장 확실하다.
- 선택안: `ALLOW_PAGES_ORIGIN=true`면 `Origin`이 **정확히** `https://bnkkosk208.github.io` 일 때만 허용(`Access-Control-Allow-Origin` 반사, `Vary: Origin`, 허용 헤더 `Content-Type, X-Local-Token`, 메서드 `GET, POST, DELETE`, 프리플라이트 `OPTIONS` 응답, PNA 프리플라이트 `Access-Control-Request-Private-Network: true`에 `Access-Control-Allow-Private-Network: true` 응답). 와일드카드 `*` 금지. 이때도 블로그 iframe 안 실거래는 막는다(최상위 창일 때만).
- 그 외 `Origin`(다른 사이트)이 붙은 요청은 `403`. `Host` 헤더가 `127.0.0.1:PORT`/`localhost:PORT`가 아니면 `403`(DNS 리바인딩 방지).
- **로컬 토큰**: 서버 시작 시 `crypto.randomBytes(24).toString('base64url')` 생성(또는 `.env`의 `LOCAL_TOKEN`), 콘솔에만 출력. 브라우저는 실거래 진입 시 토큰 입력 → `sessionStorage` 저장 → 모든 `/api/*` 요청에 `X-Local-Token` 헤더. 비교는 `crypto.timingSafeEqual`. 5회 연속 실패 시 1분간 잠금.
- 요청 바디 최대 4KB, `Content-Type: application/json`만 허용.

### 5.5 업비트 인증 (JWT) — `upbit-auth.js`
**[확인 필요: docs.upbit.com 인증 문서 — 이 세션에서는 접근 불가였음. 아래는 공개 예제·라이브러리로 교차 확인한 현행 규격]**
- 헤더 `{"alg":"HS512","typ":"JWT"}` (HS256도 허용된다는 자료가 있으나 HS512 사용).
- 페이로드: `access_key`, `nonce`(`crypto.randomUUID()`), 파라미터가 있을 때만 `query_hash`, `query_hash_alg: "SHA512"`.
- `query_hash` = 요청 파라미터를 **실제 전송하는 쿼리 문자열과 동일한 문자열**(`key=value&key=value`, 파라미터 순서 유지, URL 인코딩하지 않은 형태 **[확인 필요]**, 배열은 `key[]=v1&key[]=v2`)의 SHA-512 hex.
  - GET/DELETE: URL 쿼리 문자열 그대로.
  - POST: JSON 바디의 키를 같은 순서로 위 형식 문자열로 만들어 해시, 바디는 JSON으로 전송.
- 서명: `base64url(header) + "." + base64url(payload)`를 `crypto.createHmac('sha512', SECRET_KEY)`로 서명 → base64url. 헤더 `Authorization: Bearer <jwt>`.
- 라이브러리 없이 구현(`jsonwebtoken` 미사용). `buildQuery(params)`, `queryHash(qs)`, `makeJwt({accessKey, secretKey, qs, nonce})` 3개 함수로 분리해 테스트 가능하게(nonce 주입 가능).
- 업비트 호출 타임아웃 10초(`AbortSignal.timeout(10000)`), `Remaining-Req` 헤더를 응답에 함께 전달.

## 8. 검증 체크리스트 (Review 기준)

### 8.1 전략 계산 케이스 (`tests/lib.test.js`에 그대로 넣는다)
1. **변동성 돌파 목표가**: 전일 고가 100,000,000 / 저가 96,000,000, 당일 시가 98,000,000, K=0.5 → `target = 98,000,000 + 4,000,000 × 0.5 = 100,000,000`.
   - 가격 99,999,000 → `hold`, 100,000,000 → `buy`(같은 날 두 번째 돌파 → `hold`, memo로 확인).
   - K=0.3 → 99,200,000.
   - 다음날 09:00:00 KST(UTC 00:00:00) 이후 평가 시 보유 중이면 `sell`.
2. **SMA**: 종가 `[1,2,3,4,5]`, 기간 3 → `[null,null,2,3,4]`.
3. **골든크로스**: short=2, long=3, 종가 `[5,4,3,4,6]` → 직전(인덱스3) SMA2=3.5, SMA3=3.667(≤) / 현재(인덱스4) SMA2=5, SMA3=4.333(>) → `buy`. 종가 `[3,4,5,4,2]` → 직전 SMA2=4.5 ≥ SMA3=4.333, 현재 SMA2=3 < SMA3=3.667 → `sell`. 이미 단기>장기인 상태 유지(`[1,2,3,4,5]`) → `hold`.
4. **RSI(Wilder, period=3)**: 종가 `[10,11,12,11]` → 변화 `+1,+1,−1` → avgGain=2/3, avgLoss=1/3, RS=2, **RSI=66.67**. 다음 종가 13(변화 +2) → avgGain=(2/3×2+2)/3=10/9, avgLoss=(1/3×2+0)/3=2/9, RS=5, **RSI=83.33**. 소수 둘째 자리 반올림 비교.
   - 전부 상승 `[1,2,3,4]` → RSI=100. 변화 없음 `[5,5,5,5]` → 50.
   - 교차: prevRsi=28, rsi=31, low=30 → `buy`; prevRsi=72, rsi=69, high=70 → `sell`; prevRsi=25, rsi=27 → `hold`.
5. **캔들 정렬·마감 판정**: 최신순 입력 3개 → 과거순 출력. 60분봉 최신 캔들 시작 13:00 UTC, now=13:30 UTC → 미마감 제외, now=14:00:01 → 포함.
6. **(참고 검증)** 실제 KRW-BTC 60분봉 RSI(14)를 업비트 웹 차트의 RSI 값과 비교해 ±1 이내(업비트 차트 설정이 Wilder인지에 따라 차이 가능 — 참고만).

### 8.2 모의 체결·수수료 계산
- 초기 KRW 1,000,000. 시장가 매수 100,000원 @ 50,000,000:
  - 수수료 50원, KRW 차감 100,050 → 잔고 899,950, 수량 0.002 BTC, 평단 50,000,000.
- 같은 0.002 BTC 시장가 매도 @ 52,000,000:
  - 총액 104,000, 수수료 52, 수령 103,948 → 잔고 1,003,898.
  - 실현 손익 = 103,948 − 100,050 = **+3,898원 (+3.90%)**.
- 사용 가능 KRW 4,000원 → 매수 시도 시 주문 안 함 + "최소 주문금액 미달" 로그.
- 보유 0.00005 BTC @ 50,000,000(=2,500원) 매도 시도 → 매도 안 함 + "잔량 소액" 로그, 포지션 종료 처리.
- 1회 최대 50,000원, 설정 100,000원 → 실제 주문 50,000원.
- 비중 50%, KRW 899,950 → min(449,975, 899,950/1.0005) = 449,975원 주문.
- 일일 주문 횟수 10회 도달 → 11번째 신호에서 봇 정지.
- `floor8(0.123456789) = 0.12345678`.

### 8.4 서버 서명 검증 (실 키 없이)
- `node server/sign-check.js`: 고정값 `accessKey='test-access'`, `secretKey='test-secret'`, `nonce='00000000-0000-0000-0000-000000000000'`, 파라미터 `{market:'KRW-BTC', side:'bid', ord_type:'price', price:'10000'}` 로
  1. 쿼리 문자열 `market=KRW-BTC&side=bid&ord_type=price&price=10000` 출력
  2. 그 SHA-512가 `printf '%s' 'market=KRW-BTC&side=bid&ord_type=price&price=10000' | openssl dgst -sha512` 결과와 일치
  3. JWT 서명부가 `printf '%s' "<header>.<payload>" | openssl dgst -sha512 -hmac test-secret -binary | base64 | tr '+/' '-_' | tr -d '='` 와 일치
  4. JWT 헤더/페이로드를 base64url 디코드하면 `alg=HS512`, `query_hash_alg=SHA512`, `access_key=test-access`
  5. 파라미터 없는 요청(`/v1/accounts`)은 `query_hash` 필드가 없음
- `DRY_RUN=true`로 서버 실행 → 브라우저 실거래 모드에서 봇 매수 → 서버가 업비트에 보내지 않고 요청 내용 반환, 로그에 "DRY-RUN" 표시.
- 보안 점검: `curl -H "Origin: https://evil.example" http://127.0.0.1:8787/api/accounts` → 403. 토큰 없이 → 401. `GET /server/.env`, `GET /../../index.html` → 404/403. `Host: evil.example` → 403. `market=KRW-XRP`(허용 목록 밖), `price=60000`(한도 초과) → 400.
- 서버 응답·로그 어디에도 키 문자열이 없는지 `grep`.
- (사용자 직접, 선택) 실제 키로 `GET /api/accounts`만 호출해 인증 통과 확인 — 조회 전용이라 안전.

## 9. 위험 고지 문구 초안
> **투자 위험 고지**
> 이 앱은 개인 학습·실험용으로 만든 도구이며 투자 권유나 자문이 아닙니다. 가상자산은 가격 변동이 매우 크고 원금 전액을 잃을 수 있습니다. 앱에 포함된 전략(변동성 돌파, 이동평균 교차, RSI)과 백테스트 결과는 과거 데이터에 기반한 것으로 **미래 수익을 보장하지 않습니다**. 실거래 모드에서 발생하는 모든 주문과 그 결과(손실, 수수료, 프로그램 오류·네트워크 장애·거래소 장애로 인한 손해 포함)에 대한 **책임은 전적으로 사용자에게 있습니다**. API 키는 본인 PC에만 보관하고, 출금 권한을 절대 부여하지 마십시오. 이 앱은 업비트(두나무)와 관련이 없는 비공식 도구입니다.

짧은 버전(하단 고정): "모의투자용 학습 도구입니다. 수익을 보장하지 않으며 실거래 손실 책임은 사용자에게 있습니다."
