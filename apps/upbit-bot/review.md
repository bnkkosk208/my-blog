# Review — 업비트 자동매매 봇 (upbit-bot) v1.0.0

검증일 2026-11-11 · Review 서브에이전트(Build와 분리) · 기준: `spec.md` 8장, `.agents/upbit-bot/review.md`, `.agents/upbit-bot/build-share.md`

## 요약 — **조건부 통과**

- 자동 테스트, 서명 검증, 계산 독립 검증, 브라우저 동작(모의·DRY-RUN 실거래), 로컬 서버 보안, 배포 요건 모두 통과했다.
- 돈과 관련된 버그 **4건(높음 2, 중간 2)** 을 찾아 앱 폴더 안에서 고쳤다.
  1. 현재가가 없을 때 매도하면 포지션이 지워짐
  2. 체결 확인 중 통신이 실패하면 포지션이 기록되지 않아 중복 매수 위험
  3. 보유 포지션과 다른 마켓으로 바꾸면 그 마켓 기준으로 매도됨(실거래에서는 원래 갖고 있던 코인을 팔 수 있음)
  4. 일일 주문 한도가 청산(매도)까지 막음
- 고친 뒤 테스트는 28/28 통과하고, 브라우저 흐름도 다시 확인했다.
- "조건부"인 이유는 두 가지다.
  - 업비트 공식 문서로 확인해야 하는 값(spec 11장)이 이번에도 확인되지 않았다. 이 환경에서는 api.upbit.com과 docs.upbit.com에 접근할 수 없다.
  - 아래 "보고만" 항목은 설계를 바꿔야 해서 고치지 않았다.
- **실거래(`DRY_RUN=false`)는 실제 키로 검증하지 않았다.** 실주문 전에 사용자가 직접 `GET /api/accounts` 조회부터 시험해야 한다.

## 발견한 문제

### 높음

**H1. 현재가가 없을 때 매도하면 포지션이 사라짐** — 수정함
- 위치: `lib/bot.js:340` 부근 `executeSell`
- 재현: 새로고침 직후 시세가 들어오기 전에 "보유분 시장가 매도"를 누른다(또는 다른 마켓의 포지션을 매도한다). `canSell(qty, undefined)`가 false가 되어 "잔량 소액"으로 처리되고 `position = null`이 된다.
- 영향
  - 모의: 계좌에는 코인이 남는데 봇은 포지션을 잊는다.
  - 실거래: 봇이 산 코인을 더 이상 추적·청산하지 않는다.
- 조치: 가격이 없으면 "현재가가 없어 매도를 보류합니다" 로그를 남기고 포지션을 유지한다.

**H2. 실거래 체결 확인 중 통신 실패 → 포지션 누락 → 중복 매수 위험** — 수정함
- 위치: `lib/brokers.js` `place()` / `waitFilled()` (수정 후 214·236·259줄)
- 재현: 주문 POST는 성공했는데 `GET /api/order` 폴링 중 한 번이라도 네트워크 오류가 나면 `network` 오류가 그대로 올라간다. 봇은 주문 실패로 보고 정지하지 않으며, 포지션을 기록하지 않은 채 다음 신호에서 다시 매수할 수 있다.
  - POST 자체가 시간 초과(`upstream_unreachable`·502)인 경우에도 주문이 실제로 나갔는지 알 수 없다.
- 조치
  - 폴링 오류는 재시도하고, 끝내 확인되지 않으면 `unconfirmed`로 처리한다.
  - POST의 네트워크·5xx 오류도 `unconfirmed`로 처리한다.
  - 엔진은 `unconfirmed`를 받으면 봇을 일시정지하고 "업비트에서 주문 내역을 직접 확인하세요"를 안내한다.
  - 업비트의 4xx(잔고 부족 등)는 결과가 명확하므로 기존대로 처리한다.

### 중간

**M1. 보유 포지션과 다른 마켓으로 바꾸면 그 마켓으로 매도·손절·재시작됨** — 수정함
- 위치: `lib/bot.js`(포지션에 마켓 없음), `main.js` `changeMarket`
- 재현: KRW-BTC 포지션을 보유한 채 봇을 정지하고 KRW-ETH로 바꾼 뒤 "보유분 시장가 매도" 또는 재시작을 한다.
  - `config.market = KRW-ETH`로 `min(봇 수량, ETH 잔고)`를 매도한다.
  - 실거래에서 `ALLOWED_MARKETS`에 ETH가 있으면 사용자가 원래 보유하던 ETH를 팔 수 있다. 이는 결정 D5 위반이다.
  - 손절 판정도 다른 마켓 가격으로 한다.
- 조치
  - 포지션에 `market`을 기록한다.
  - 매도와 수동 매도는 포지션 마켓 기준으로 한다.
  - 다른 마켓으로 시작하면 거부한다.
  - 손절은 마켓이 같을 때만 판정한다.
  - 화면에서는 포지션이 있는 동안 마켓 변경을 막고 안내한다.
  - 이 수정 전에 저장된 포지션(market 없음)에는 화면 쪽 차단만 적용된다.

**M2. 일일 주문 한도가 청산 매도까지 막음** — 수정함
- 위치: `lib/bot.js` `checkDailyLimit` / `executeSell`
- 재현: 한도가 홀수이거나 손절 등으로 횟수가 홀수인 상태에서 마지막 주문이 매수이면, 매도 신호와 손절이 막힌 채 봇이 정지하고 보유분이 방치된다.
- 조치
  - 매수는 청산 1회분을 남겨 둘 때만 허용한다(`count + 1 < max`).
  - 매도는 한도로 막지 않는다.
  - 청산 후 더 매수할 수 없으면 봇을 자동 정지한다.
  - 총 주문 수는 한도를 넘지 않는다.
  - spec 8.2("10회 도달 → 11번째 신호에서 정지")도 그대로 성립한다.
  - 다만 한도가 1이면 매수가 일어나지 않는다.

**M3. 서버가 매도 수량에 상한을 두지 않음** — 보고만
- 위치: `server/server.js:201`
- `ask`는 허용 마켓이기만 하면 수량 제한 없이 통과한다(DRY-RUN에서 `volume=100` 수락을 확인).
- "봇이 산 수량만 매도"는 브라우저만 지킨다. 토큰이 유출되거나 브라우저 코드에 버그가 있으면 허용 마켓의 기존 보유분 전량이 시장가로 매도될 수 있다.
- 출금이 아니므로 자산이 외부로 빠져나가지는 않는다. 서버가 봇 매수 수량을 기억하는 설계 변경이 필요해 보고만 한다.
- 권장: `ALLOWED_MARKETS`에는 봇 전용으로 쓰는(원래 보유하지 않은) 마켓만 넣으라고 README에 안내한다.

**M4. 서버 일일 한도도 청산 매도를 막을 수 있음** — 보고만
- 위치: `server/server.js:211`
- 서버는 매도도 한도에 세고, 실패하거나 거부된 주문도 셀 수 있다(검증 통과 후 업스트림 실패분 포함). 재시작하면 0으로 초기화된다.
- 브라우저와 서버 한도가 같은 기본값(10)이면, 서버가 브라우저보다 먼저 한도에 닿아 청산이 400으로 막힐 수 있다(재현: 10회 후 `ask` 거부 확인).
- 권장: 서버 `DAILY_MAX_ORDERS`를 브라우저 한도보다 크게 잡도록 README·`.env.example`에 안내하거나, 서버에서 매도는 한도 예외로 둔다(정책 결정 필요).

### 낮음

**L1. 투자 금액 입력 칸이 100% 폭으로 늘어남** — 수정함
- 위치: `style.css:216`
- `.field .input { width:100% }`가 `.num-input`보다 우선해서 "원"·"%" 단위가 줄바꿈되어 홀로 남았다.
- 조치: `.field .invest-row .num-input` 폭을 110px·64px로 고정. 375px에서 재확인했다.

**L2. README의 실거래 진입 체크 개수 불일치** — 수정함
- 위치: `server/README.md:58`
- "체크 3개"로 되어 있었으나 화면은 배포 면책을 더한 4개다. 4개로 고쳤다.

**L3. `python -m http.server`로 열면 `/health` 404가 10초마다 콘솔 오류로 남음**
- 위치: `ui/live-gate.js` 서버 모니터
- 로컬 주소에서는 노드 서버인지 알 수 없어 확인하기 때문이다. 기능에는 영향이 없다. GitHub Pages(블로그)와 `node server` 출처에서는 발생하지 않는다. 보고만 한다.

**L4. 변동성 돌파 매수가 실패해도 그날 재시도하지 않음**
- 위치: `lib/strategies.js:125`
- 매수 신호 시점에 `memo.enteredDay`가 기록되므로, 최소 금액 미달이나 일시적 통신 오류로 주문이 실패해도 당일 재진입하지 않는다. 손실 쪽으로는 안전한 동작이라 보고만 한다.

**L5. 셸 환경변수가 `.env`보다 우선함**
- 위치: `server/env.js:27`
- PC에 `DRY_RUN`·`PORT` 같은 환경변수가 이미 있으면 `.env` 값이 무시된다. 문서화를 권장한다. 보고만 한다.

**L6. 하단 고지바의 "자세히" 버튼 높이 32px**
- 위치: `style.css:282`
- 터치 권장치 44px보다 작다. 의도된 축소(바 높이 유지)로 보이며 보고만 한다. 나머지 버튼·입력은 44px 이상이고, 체크박스·라디오는 라벨 전체(≥44px)가 터치 영역이다.

**L7. 토큰 5회 실패 잠금이 전역**
- 같은 PC의 다른 프로그램이 틀린 토큰을 반복하면 정상 브라우저도 1분간 잠긴다. 로컬 전용이라 영향이 적어 보고만 한다.

### 코드 리딩
- **경계 계산**: 매수가격선·익절선·손절선을 `가격 × (100 ± N) / 100`으로 계산하고, 비교에 상대 오차 1e-12를 허용한다(`atOrAbove`/`atOrBelow`). 정확히 −10%·+10%인 가격에서 신호가 난다. 테스트로 확인했다.
- **같은 날 재진입 금지**: 매수 신호 때 `memo.enteredDay`에 그날 일봉 시작 시각을 적는다. 그래서 그날 손절하거나 익절한 뒤에는 다시 사지 않는다. 다만 전날 산 포지션을 오늘 매도했다면, 오늘은 아직 진입하지 않은 날이라 오늘 매수가격선 아래에서 다시 살 수 있다. 이는 규격("같은 일봉 1회 진입")에 맞다.
- **vb 전용 로직**: 다음날 자동 청산(`heartbeat`의 timer 분기, `evalVb`의 '새 일봉 시작 — 청산')은 계속 `strategyId === 'vb'` 조건에서만 돈다. dip은 날짜가 바뀌어도 보유를 유지한다(엔진 테스트로 확인).
- **isPriceBased 변경**: 원래 `=== 'vb'`였던 네 곳(scheduleNext, refreshCandles, start의 lastT, evaluate의 틱 필터)을 `vb || dip`으로 바꿨다. vb 경로의 동작은 그대로다. 기존 vb 테스트도 모두 통과한다.
- **설정 탭 손절·익절과 함께 켤 때**: `checkRisk`가 전략 판정보다 먼저 돌아 설정 탭 비율로 먼저 매도한다. 같은 날 재매수는 `enteredDay`가 막는다. 설정 탭 비율이 dip 비율보다 작으면 dip 익절·손절선보다 먼저 청산되는 것이 의도된 우선순위다.
- **실거래(LiveBroker) 경로**: `executeSell`이 `min(봇 포지션 수량, 실제 잔고)`만 매도하고, 서버 장부도 봇 매수 수량을 넘는 매도를 거절한다. 계좌에 원래 코인이 더 있어도 dip 익절 수량이 봇이 산 수량을 넘지 않는다(가짜 live 브로커 테스트를 추가해 확인).
- **백테스트 체결 가정**:
  - 선에 닿으면 선 가격에 체결한다.
  - 시가가 이미 선을 넘었으면 시가에 체결한다. 이 경우 선 가격이 아닌 불리한 쪽 가격이다.
  - 같은 캔들에서 익절선과 손절선에 모두 닿으면 손절로 친다.
  - 매수한 캔들에서는 익절하지 않는다.
  - 매도한 캔들에서는 재매수하지 않는다.
  - 결과적으로 낙관적이지 않고 보수적인 쪽이다. 화면에도 "체결 가정"으로 표시된다. 실시간 봇은 전날 산 것을 오늘 판 뒤 오늘 다시 살 수 있지만, 백테스트는 이 경우를 생략한다. 백테스트가 실제보다 거래를 적게 잡을 수 있다.
